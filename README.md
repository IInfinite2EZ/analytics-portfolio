# Анализ клиентской базы интернет-магазина: RFM, статистика, тренд

Полный аналитический цикл (SQL → Python → статистика → Power BI) на данных о продажах британского интернет-магазина подарочных товаров за 2009–2011 годы.

**Ключевой результат:** 14.9% клиентов («Лояльные» по RFM-сегментации) приносят 61.6% всей выручки. Различия среднего чека между странами статистически подтверждены (Kruskal-Wallis, p ≈ 5.2×10⁻¹³⁴).

## Данные

Источник: [Online Retail II](https://archive.ics.uci.edu/dataset/502/online+retail+ii) (UCI ML Repository). ~1 млн транзакций британского интернет-магазина подарочных товаров, декабрь 2009 – декабрь 2011. Компания в основном работает с оптовыми покупателями.

Известные ограничения данных:
- часть строк без Customer ID
- встречаются служебные корректировки с отрицательной ценой при положительном количестве
- последний месяц данных неполный (9 дней вместо 31)

## Стек

SQL (MySQL) — агрегация, оконные функции, CTE. Python (pandas, scipy, matplotlib) — очистка, RFM-сегментация, статистические тесты. Power BI — дашборд.

## 1. Подготовка данных (SQL)

Три отдельные агрегации под разные задачи: выручка по странам на уровне счёта, выручка по месяцам для тренда, база для RFM по клиентам.

RFM-база строится через CTE с оконными функциями — Recency считается как разница между последней датой в данных и последней покупкой клиента, Monetary — суммой через `OVER (PARTITION BY)`. Frequency вынесен в отдельный CTE с `COUNT(DISTINCT Invoice)`, потому что MySQL не поддерживает `DISTINCT` внутри оконных функций:

```sql
with customer_revenue as
(select * from online_retail
 where Quantity > 0 and `Customer ID` is not null and Price > 0),
freq as
(select `Customer ID`, count(distinct Invoice) as F
 from customer_revenue
 group by `Customer ID`),
t as
(select `Customer ID`, InvoiceDate,
        max(InvoiceDate) over () as max_d,
        max(InvoiceDate) over (partition by `Customer ID`) as customer_m_d,
        sum(Quantity * Price) over (partition by `Customer ID`) as M
 from customer_revenue)
select distinct t.`Customer ID`,
       TIMESTAMPDIFF(DAY, t.customer_m_d, t.max_d) as R,
       freq.F,
       t.M
from t
join freq on t.`Customer ID` = freq.`Customer ID`
```

Условие `Price > 0` добавлено после обнаружения аномалии на этапе статистического анализа (см. пункт 3) — часть строк содержит служебные корректировки с отрицательной ценой при формально положительном количестве, которые искажали бы Monetary.

## 2. RFM-сегментация клиентов

Присвоил каждому клиенту оценки 1–5 по Recency, Frequency, Monetary через квантильное разбиение (`pd.qcut`). Для Frequency пришлось использовать `duplicates='drop'`, так как распределение сильно скошено — большая доля клиентов сделала всего одну покупку, из-за чего квантили давали повторяющиеся границы.

**Первая версия** сегментации (4 правила + категория «Прочие») оставила **42.9%** клиентов в «Прочих» — по сути, бесполезный результат для бизнеса:

```python
def segment(x):
    r, f, m = x['R_score'], x['F_score'], x['M_score']
    if r >= 4 and f >= 4 and m >= 4:
        return 'Лояльные'
    elif r <= 2 and f >= 4 and m >= 4:
        return 'В зоне оттока'
    elif r >= 4 and f <= 2:
        return 'Новые'
    elif r <= 2 and f <= 2 and m <= 2:
        return 'Потерянные'
    else:
        return 'Прочие'
```

**Доработанная версия** — добавил промежуточные правила («Уходящие», «Новые с высоким чеком», «Частые с низким чеком», «Стабильные средние»), чтобы каждая группа несла содержательный смысл:

```python
def segment(row):
    r, f, m = row['R_score'], row['F_score'], row['M_score']
    if r >= 4 and f >= 4 and m >= 4:
        return 'Лояльные'
    elif r <= 2 and f >= 4 and m >= 4:
        return 'В зоне оттока'
    elif r <= 2 and f >= 3 and m >= 3:
        return 'Уходящие'
    elif r >= 4 and f <= 2 and m >= 3:
        return 'Новые с высоким чеком'
    elif r >= 4 and f <= 2:
        return 'Новые'
    elif r <= 2 and f <= 2 and m <= 2:
        return 'Потерянные'
    elif f >= 4 and m <= 2:
        return 'Частые с низким чеком'
    elif r == 3 and f == 3 and m == 3:
        return 'Стабильные средние'
    else:
        return 'Прочие'
```

## 3. Статистика: различается ли средний чек между странами

Отобрал топ-6 стран по количеству заказов и проверил гипотезу о равенстве среднего чека между ними.

**Обнаруженная аномалия:** при первом построении распределений выручки по счетам гистограмма по United Kingdom оказалась сильно растянута из-за одного счёта с выручкой 168 469. Разобрал причину в два шага:

1. Часть счетов имела отрицательную выручку — служебные корректировки, а не реальные продажи. Исключил их (`Revenue > 0`).
2. Счёт № 581483 содержал одну позицию товара («PAPER CRAFT, LITTLE BIRDIE») с количеством 80 995 штук — при проверке через SQL это оказалась единственная строка в счёте, что нетипично для легитимного опта (тот обычно распределён по многим позициям). Признал вероятной ошибкой ввода данных и исключил из анализа.

![Распределение выручки по странам](images/histograms.png)

**Тест Левена:** statistic = 80.55, p ≈ 2.1×10⁻⁸⁴ → дисперсии между странами значимо неравны, условия для классической ANOVA не выполняются.

**Kruskal-Wallis:** statistic = 630.49, p ≈ 5.2×10⁻¹³⁴ → как минимум в одной стране медиана чека статистически значимо отличается от других.

**Пост-хок тест Данна** (с поправкой Бонферрони) показал, что United Kingdom статистически отличается от всех остальных рынков, а континентальная Европа (Germany, France, Spain) образует статистически близкую группу между собой — что согласуется с бизнес-моделью: UK — розничный рынок с высоким объёмом мелких заказов, остальные страны — преимущественно оптовые закупки.

## 2. Колл-центр на аутсорсе: какие сценарии обзвона вернуть, а какие оставить в прошлом

> **О данных.** Все данные, названия сценариев, цифры и правила в этом разделе вымышлены и собраны только для того, чтобы показать методологию. Реальный проект охватывал несколько тысяч файлов; рабочие данные и условия работы с подрядчиком не раскрываются в целях конфиденциальности.

**Ключевой результат (на демонстрационных данных):** после отключения четырёх из шести сценариев нагрузка на колл-центр за январь–май упала с 812 до 361 контакта, то есть **на 55%**. Мой анализ показал, какие сценарии стоит вернуть (один из них в изменённом виде), а какие оставить выключенными. Возврат двух сценариев мог бы поднять нагрузку до ≈712 контактов (88% прежнего уровня). В реальном проекте руководство приняло рекомендации с минимальными правками.

### Задача

Каждый день в колл-центр на аутсорсе уходят выгрузки: списки людей, которым нужно позвонить по определённому сценарию (скрипту). Сценарии бывают двух типов: уведомить клиента об отправленном запросе или получить его электронную почту, чтобы запрос вообще можно было отправить. Колл-центр оплачивается, а значит, его мощности должны работать на пользу.

Часть сценариев в какой-то момент отключили, и вопрос «а как это повлияло?» остался без ответа. Моя задача: собрать данные по всем выгрузкам за 2025 и 2026 годы, сравнить сопоставимые периоды и решить по каждому сценарию, **возвращать его, оставлять или менять**.

### Как устроены данные

Один файл Excel — это один сценарий за один день отправки. Внутри четыре колонки: номер убытка, имя, телефон, регион. Строка файла — один человек, которому нужно позвонить. Файлы лежат в папках по датам.

| 2025: в один день уходило 6 файлов | 2026: остались только 2 |
|---|---|
| ![День отправки 2025](images/case2_folder_2025.png) | ![День отправки 2026](images/case2_folder_2026.png) |

![Файл сценария](images/case2_file.png)

### Проблема: данные «гуляют»

Файлов много (в реальном проекте их тысячи), а выгружались они в разное время и по-разному. Самое наглядное: у файлов 2025 года в имени нет года, у файлов 2026 он есть.

![Общая папка с файлами](images/case2_common_folder.png)

В реальных выгрузках к этому добавлялись ещё и отличия в столбцах: где-то лишние колонки, где-то другой порядок. Чистить каждый файл по отдельности при таком объёме нереально.

### Решение: опереться на то, что есть в каждом файле

Вместо того чтобы приводить к единому виду все столбцы, я нашёл то, что **гарантированно есть всегда**:

- в таблице внутри файла всегда есть номер убытка;
- в **имени** файла всегда есть дата и номер сценария.

Поэтому из каждого файла я оставил только эти три вещи: номер убытка, сценарий, дата. Остальное в анализе не нужно.

Всё это собрано в Power Query одним запросом, который читает папку целиком. Ключевые шаги (полный код в папке `/powerquery`):

```m
// 1. Читаем все файлы папки и отбрасываем временные файлы Excel (~$...)
Источник = Folder.Files("<путь к папке>\Сценарии\Общая база"),
#"Строки с примененным фильтром" =
    Table.SelectRows(#"Текст в нижнем регистре", each not Text.StartsWith([Name], "~$")),

// 2. Делим имя файла по первому пробелу: «02.02» | «сценарий 1.xlsx»
#"Разделить столбец по разделителю" = Table.SplitColumn(...,
    Splitter.SplitTextByEachDelimiter({" "}, QuoteStyle.Csv, false), {"Name.1", "Name.2"}),

// 3. У файлов 2025 года в имени нет года (02.02): достраиваем его
#"Добавлен пользовательский объект1" = Table.AddColumn(..., "Пользовательский",
    each if Text.Length([Name.1]) = 5 then [Name.1] & ".2025" else [Name.1]),

// 4. Считаем строки: сколько контактов ушло по каждому сценарию в каждый день
#"Сгруппированные строки" = Table.Group(..., {"Name.2.1", "Пользовательский"},
    {{"Количество", each Table.RowCount(_), Int64.Type}})
```

![Power Query: применённые шаги и результат](images/case2_pq.png)

**Одно допущение, которое стоит назвать прямо:** файл без года в названии считается файлом 2025 года. Для этих данных это верно, но в другой структуре папок такое правило пришлось бы пересматривать.

### Ловушка сопоставимости

Данные 2026 года доступны только по май включительно. Если сравнить пять месяцев 2026 с полным 2025, любой сценарий «потеряет» половину объёма просто из-за длины периода. Поэтому в обоих годах я сравнивал **одни и те же месяцы, январь–май**.

### Решение по каждому сценарию

Объём нужен, но недостаточен: решение зависит и от того, что изменилось вокруг сценария.

![Решения по сценариям](images/case2_decisions.png)

| Сценарий | Решение | Почему |
|---|---|---|
| **1** | Оставить | Стабильный объём, в 2026 даже вырос |
| **2** | **Вернуть** | Максимальный объём из всех сценариев, а правил, которые бы его заменили, не вводилось |
| **3** | Не возвращать | Он создавался против «зависших» убытков, а их стало меньше 10 (85 в 2025 против 7 в 2026). Возвращать дороже, чем выгода |
| **4** | **Вернуть в изменённом виде** | Был третьим по объёму, но потерял смысл: куратор теперь сам звонит клиенту на следующий день, и звонки задваивались. Предложил сдвинуть отправку на 3-й рабочий день, чтобы она напоминала о недавнем разговоре и срабатывала, если куратор не дозвонился |
| **5** | Оставить | Объём растёт, в 2026 вырос на 17% |
| **6** | Не возвращать, заменить правилом | В среднем 2,4 контакта за день: куратору проще и быстрее позвонить самому, чем поддерживать отдельный сценарий |

### Как я проверил, что спрос на выключенные сценарии не исчез

Главный риск в таком анализе: объём выключенного сценария в 2025 году мог держаться на потоке обращений, которого в 2026 уже нет. Тогда «вернуть» значило бы вернуть пустоту.

Проверка: сценарии 1 и 5 работали в **оба** года, так что они выступают контрольными. Их суммарный объём за январь–май **не упал, а вырос на 8,4%** (333 → 361 контакт). Значит, поток обращений остался прежним, и оценка спроса по 2025 году разумна.

### Потенциал рекомендаций

Если поток обращений прежний, то возврат сценария 2 добавляет до +191 контакта (+53% к текущей нагрузке), а изменённый сценарий 4 ещё до +160. В сумме нагрузка могла бы вернуться к ≈712 контактам, это около 88% уровня 2025 года. Это оценка сверху: объём изменённого сценария 4 мог бы отличаться от прежнего.

### Ограничения и что сделал бы иначе

- Оценка потенциала строится на предположении, что поток обращений остался прежним. Контрольные сценарии это поддерживают, но не доказывают.
- Анализ сравнивает объём, но не учитывает стоимость звонка и то, насколько звонок помогает. Следующим шагом добавил бы стоимость и долю контактов, после которых клиент действительно отвечает на запрос.
- Решения принимались на основе описательных показателей, без статистических тестов и без контрольной группы: мне важно было быстро дать практичную рекомендацию, а не строго измерить причинность.
- Путь к папке в запросе Power Query задан жёстко. В следующей версии вынес бы его в параметр, чтобы запрос можно было запустить на любой машине без правки кода.

## 3. Анализ клиентской обратной связи (CSI/NPS): что стоит за низкой оценкой

> **О данных.** Все данные в таблице ниже (номера убытков, комментарии клиентов, решения, предложения) вымышлены и созданы только для иллюстрации методологии. Реальные данные компании и партнёров не раскрываются в целях конфиденциальности.

**Ключевой результат:** за период работы над задачей разобрал 67 обращений с низкими оценками, сформулировал 23 предложения по улучшению процессов, более 15 из них приняты руководством. Эти цифры взяты из реальной работы, а таблица ниже лишь показывает, как выглядел процесс.

### Задача

Раз в месяц партнёр присылает выгрузку клиентских оценок: **CSI** (насколько клиент доволен решением по своему случаю) и **NPS** (порекомендует ли он нас другим), плюс короткая выжимка того, что клиент сказал по телефону. Низкой в компании считается оценка **от 1 до 6 включительно**.

### Как проходил разбор

1. **Фильтр.** Отбирал случаи, где CSI или NPS попадает в диапазон 1–6.
2. **Что говорит клиент.** Читал комментарии и искал в них реальную претензию. Часто она не совпадала с поставленной оценкой.
3. **Расследование.** Открывал сам случай и смотрел всё: кто куратор, историю изменений, какие запросы направлялись, были ли звонки, что клиент предоставил с самого начала. В спорных случаях слушал запись звонка, чтобы понять, чья версия верна.
4. **Вердикт.** Определял, была ли ошибка с нашей стороны, и фиксировал нейтральной формулировкой.
5. **Предложение.** Решал, что с этим делать и кому это адресовать.

### Куда уходит предложение

| Ситуация | Куда адресуется |
|---|---|
| Ошибка в обработке случая | **Внутреннее** предложение (например, разбор с куратором), наружу не выносится |
| Решение верное, но клиент не получил нужной коммуникации | **Внутреннее** (например, новый алгоритм звонков клиентам) |
| Решение верное, но клиент не понял условия или не нашёл информацию | **Для партнёра** (прозрачность информации для клиентов) |

Не каждый разбор заканчивается предложением: иногда низкая оценка не имеет управляемой причины, и честнее зафиксировать это, чем придумать вывод.

### Главный инсайт

**Низкая оценка почти никогда не означала ошибку.** В подавляющем большинстве случаев решение было корректным, а клиент всё равно был недоволен. Причины повторялись: размер выплаты оказался ниже ожиданий, никто не позвонил и не объяснил, непонятно, где прочитать условия. Значит, чинить нужно не решения, а то, как они объясняются, и именно в эту сторону пошла основная часть моих предложений.

### Ограничения и что сделал бы иначе

- Оценки собираются телефонным опросом, и у меня на руках только краткая выжимка разговора, а не полная запись.
- Эффект принятых предложений нельзя строго измерить без контрольной группы: сравнение «до и после» не отделяет их влияние от остальных изменений.
